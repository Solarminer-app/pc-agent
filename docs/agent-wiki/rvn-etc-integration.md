### Observed Stratum handshake, 2026-10-03

Using the installed SRBMiner-MULTI 3.7.1 and the visible Windows RTX 2080 Ti, a local fake pool recorded these initial miner calls. No real share was mined or submitted:

| Coin | Miner subscribe | Miner authorize | Additional call |
| --- | --- | --- | --- |
| RVN | `params:["SRBMiner-MULTI/3.7.1"]` | `params:["RVN_ADDRESS", "x"]` | `mining.extranonce.subscribe` |
| ETC | `params:["SRBMiner-MULTI/3.7.1", "EthereumStratum/1.0.0"]` | `params:["0xETC_ADDRESS", "x"]` | `mining.extranonce.subscribe` |

Passing a separate `--worker` argument for RVN did **not** change the observed authorize username; the upstream address cannot simply be encoded in that argument. A `--wallet ADDRESS.WORKER` login was observed in the earlier probe, so any dynamic routing encoding must be checked there and removed by the proxy before upstream authorize. These observations do not prove submit layout or miner acceptance of target switches.

Read-only TCP probes to 2Miners using the public example addresses (no `mining.submit`) returned:

- RVN `subscribe.result:["065bbf80","49"]`, authorize `true`, `mining.set_target` with a 64-digit hex target, `mining.notify` with eight parameters including job ID at index 0, then extranonce-subscribe `true`.
- ETC `subscribe.result:[["mining.notify", SESSION_ID, "EthereumStratum/1.0.0"], EXTRANONCE]`, authorize `true`, `mining.set_difficulty`, four-parameter `mining.notify` with job ID at index 0, extranonce-subscribe `true`, then `mining.set_extranonce`.

The two target/difficulty and subscribe shapes are different. The [EthereumStratum/1.0.0 specification](https://github.com/nicehash/Specifications/blob/master/EthereumStratum_NiceHash_v1.0.0.txt) describes ETC-style submit as `[worker, jobId, nonce]`, but the installed miner's actual submit and 2Miners acceptance still need capture. RVN submit shape and extranonce switching remain unverified. Probe scripts are local-only under workspace `.codex-qa/`; they contain public documentation example addresses and no secrets.

Two bounded ETC fake-pool mining attempts (75 and 60 seconds) replied to the installer's subscribe/authorize/extranonce calls with a captured 2Miners job and easy difficulty. Neither produced `mining.submit`; both SRBMiner processes were terminated at the timeout. The cause is not established from this probe. Do not treat the synthetic adapter tests as proof that SRBMiner accepts a switched fee job.

## Current code and implementation order

1. PC-Agent now has `GpuCoinMinerService` for RVN/KAWPOW and ETC/ETCHash, reusing the verified SRBMiner installer, GPU inventory/power service and Pearl GPU ID mapping. It persists separate pool/wallet/worker/GPU selections, validates RVN Base58Check mainnet versions and ETC 0x hex format, puts `ADDRESS.sm1.BASE64URL_POOL.WORKER` in `--wallet`, and checks the configured SolarMiner proxy, live listener and house fee target in the final start path. It monitors jobs and fee readiness, stops stale/failed processes, separates Pearl and GPU-coin process ownership, and exposes status, GPU control, console, fees and local forms. General power/PV dispatch chooses the selected GPU coin. The UI has explicit, non-toggle GPU prerequisites. This is **prepared code**, not proof of mining support. No default/donation payout is offered without a real wallet.
2. Proxy has BTC/XMR/PRL listeners. RVN and ETC now have distinct registered prototype adapters, with no listener port configured. The planned login envelope is `ADDRESS.sm1.BASE64URL_POOL.WORKER` in SRBMiner's `--wallet`; the proxy removes this suffix before forwarding `ADDRESS.WORKER` to the user pool. Fake-pool tests cover job/submit ID mapping and target replay for both observed dialect shapes. Actual miner submits, accepted shares, reconnect, TLS and fee switching remain unverified; do not enable a listener from this code alone.
3. Fee backend now has canonical RVN/ETC configs and aliases with the operator-supplied house addresses on native 2Miners accounts. Its response marks the house target explicitly; the proxy's existing DTO accepts that flag. The PC-Agent validates the RVN Base58Check address and ETC 0x format. Address ownership, central deployed configuration, actual pool credit, referral accounts and proxy refresh remain unverified. Unknown coins still return HTTP 200 and empty targets; that is not a working route.
4. Node core/frontend needs coin metadata and address validation, pool/agent DTOs, PV control, monitoring, units, revenue and payout state. Existing BTC Lightning and Braiins data must stay coin-specific. Admin portal may store RVN/ETC referral addresses now, while both routing flags remain false. Pool API accounting, balances, payouts and reconciliation are not implemented.
5. Release only after real RTX 2080 Ti / Windows 11 and Linux coverage where claimed, user/house/referrer accepted-share and payout reconciliation, PV stop/restart, migration, BTC/XMR/PRL regression, deployment ports and rollback. The local Windows GPU is visible to `nvidia-smi`; Docker Desktop access was denied to this sandbox, so no container or GPU mining test ran.

## Public price and mining-network data, 2026-10-04

The public Currency-Service now owns persisted C9 snapshots for `ravencoin` and `ethereumclassic`. It reads public 2Miners aggregate network statistics, CoinGecko USD prices and derives the base reward from each chain height: Ravencoin's 5,000 RVN initial subsidy halves every 2,100,000 blocks; Ethereum Classic follows ECIP-1017's 20% reduction every 5,000,000 blocks. Responses carry H/s, difficulty, observed block seconds, native base reward, price, source, age and a two-hour stale bound. The PC-Agent consumes only the central `currency.solarminer.app/api/v1/public/mining-networks` route and can calculate both forecasts from local KAWPOW/ETCHash workers.

This completes only the new-coin guide's currency/network-data item. Wallet validation, miner command, proxy/fee routing, pool/portal accounting, hardware and rollout were not changed and are non-applicable to this changeset; their existing gates are not satisfied by a forecast. In particular, 2Miners' public network response is not user/house/referral share credit. Provider fixture, persistence, public-contract and consumer tests pass, but the central domain returned Traefik 404 before deployment; public rollout and restart persistence remain unverified.

### Subscribe deadlock fixed; GPU execution still fails, 2026-10-04

- Operator-account SRBMiner 3.7.0 with extended local logging showed the concrete Stratum deadlock: it sends `mining.subscribe` (id 1), waits for the reply, and only then sends `mining.authorize` (id 2). The GPU proxy previously waited for authorize to learn the dynamic pool and therefore never replied to subscribe. The proxy now sends a provisional coin-shaped subscribe result, then sends `mining.set_extranonce` with the real upstream nonce and suppresses the duplicate upstream subscribe reply. RVN and ETC protocol tests cover this order. The PC-Agent `bootRun` embedded the rebuilt proxy; both managed coins connected to their Kryptex pools and received jobs on NVIDIA GPU ID 1. SRBMiner reported nonzero pool uptime and recent jobs for both.
- This revealed a separate local GPU failure. With the proxy and also with **direct Kryptex connections**, SRBMiner 3.7.0 logged `Couldn't set epoch 608 on GPU1` for RVN and `Couldn't set epoch on GPU1` for ETC, then `GPU worker thread 0 stopped`. Each direct run stayed at 0 H/s with zero submitted/accepted shares. ETC also failed with SRBMiner's documented `--gpu-table-slow-build` option. These direct controls isolate the zero-hashrate failure from the SolarMiner proxy; the installed miner/driver/GPU combination still needs hardware-level resolution. No driver, firmware or security settings were changed.
- PC-Agent now calls a GPU coin healthy only when a recent pool job **and positive hashrate** are present. A process that receives jobs but never hashes is stopped with an explicit GPU/miner diagnostic after 180 seconds; a previously hashing process is stopped after 120 seconds without positive hashrate. This avoids showing `MINING` for a worker whose GPU thread has stopped. `:pc-agent:test --offline` and focused proxy tests pass on JDK 21. No user, house or referral share, pool credit, payout or fee-switch accounting was verified. Keep release gates closed.

### GPU-ID cross-check, 2026-10-04

- `SRBMiner-MULTI.exe --list-devices` lists `GPU0` as the integrated `amd_radeon_tm__graphics` at PCI `7e:00.0`, explicitly `iGPU: disabled by default`, and `GPU1` as `nvidia_geforce_rtx_2080_ti` at PCI `01:00.0`. `nvidia-smi` reports the same RTX at `00000000:01:00.0` as NVIDIA index 0. `LocalGpuPowerService` selects that NVIDIA device; `PearlMinerService.mappedGpuId` resolves its PCI address to SRBMiner ID 1, which `GpuCoinMinerService` passes to `--gpu-id`. SRBMiner's live log names `GPU1 RTX 2080 Ti` before the epoch failure. A Radeon/NVIDIA ID mix-up is therefore ruled out for this host; the epoch failure remains inside the RTX/SRBMiner/driver execution path.

### Research on `Couldn't set epoch`, 2026-10-04

- The message is a final symptom, not a unique error code. In a [case answered by the SRBMiner author](https://bitcointalk.org/index.php?topic=5190081.700), an old AMD driver could not allocate the >4 GB FiroPow DAG despite nominally sufficient 8 GB VRAM. A [separate SRBMiner report](https://bitcointalk.org/index.php?topic=5190081.msg65230660) prints `not enough free memory [need 7018 MB : have 5513 MB]` immediately before the same epoch message on NVIDIA. These establish concrete memory/driver-allocation cases, not this host's root cause.
- For the local RTX, a simple total-capacity shortage is not supported: the miner reported roughly 9.4 GB free and no `not enough free memory` line, while [Kryptex estimates RVN epoch 608 at 5,888 MB and current ETC at about 4,400 MB](https://pool.kryptex.com/rvn/dag-size-calculator). An individual OpenCL allocation or a changing Windows process memory budget can still fail; [Microsoft documents WDDM process residency budgets](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/driver-residency-in-wddm-2-0). No OpenCL return code or budget measurement was captured here.
- The [SRBMiner author's Windows bug acknowledgment and a later RTX 4090 report with the same epoch symptom](https://bitcointalk.org/index.php?topic=5190081.msg66924625) make a miner/Windows/driver interaction plausible. They do not establish a 3.7.0 regression. NVIDIA [documents a 610+ OpenCL buffer-size behavior change](https://docs.nvidia.com/datacenter/tesla/tesla-release-notes-615-71-09/index.html); the local miner reports a 10.7 GB maximum buffer, however, so this particular limit does not directly explain a 5.9 GB DAG. NVIDIA also lists a >2 GB OpenCL-buffer issue as **fixed** in 616.56 in its [GeForce release discussion](https://www.nvidia.com/en-us/geforce/forums/game-ready-drivers/13/589348/geforce-grd-61656-feedback-thread-released-82626/3623585/); this is not evidence that installed 616.92 has that issue.
- The local direct-pool controls rule out the SolarMiner proxy as the cause of 0 H/s, and the PCI/device listing rules out iGPU assignment. ETC still fails with [SRBMiner's `--gpu-table-slow-build`](https://github.com/doktor83/SRBMiner-Multi/blob/master/Parameters), so merely slowing DAG creation did not resolve it. The next discriminating test is a bounded direct-pool run on the same RTX with another miner or SRBMiner version, recording its complete GPU/OpenCL error and available memory; only then consider a controlled driver comparison. No driver changes or successful shares are claimed.

### GPU-only algorithm parameter fixes local hashing, 2026-10-04

- The PC-Agent command used SRBMiner's generic `--algorithm` option for RVN and ETC. SRBMiner documents both that generic option and the GPU-only `--algorithm-gpu` option, while its packaged RVN/ETC launch scripts use the latter. On the available Linux host, the managed generic RVN run received live proxy jobs but logged `not enough free memory [need 2271 MB : have 1306 MB]` repeatedly and stayed at 0 H/s on a 24 GB Titan RTX.
- A controlled comparison kept SRBMiner-MULTI 3.7.1, GPU ID 0, wallet route, local proxy, API and all other relevant arguments unchanged and replaced only `--algorithm` with `--algorithm-gpu`. RVN reached 31.80 MH/s KAWPOW. ETC created its 4415 MB DAG and reached 55.38–55.45 MH/s ETCHash. Driver 580.178.04 reported about 24 GB free before the runs. Both diagnostic miners were stopped after the bounded checks.
- `GpuCoinMinerService` now emits `--algorithm-gpu` for both algorithms, with a focused command-construction regression test. This resolves the reproduced zero-hashrate cause on the tested Titan RTX/Linux host and makes a parameter error in our program the supported explanation. It does not retroactively establish the exact internal SRBMiner allocation behavior, and it has not yet been repeated on Windows or the RTX 2080 Ti.
- No share was accepted during the short confirmation windows. User/house/referral share accounting, fee switching, pool credit, payout, Windows/RTX 2080 Ti and rollout gates therefore remain open.
