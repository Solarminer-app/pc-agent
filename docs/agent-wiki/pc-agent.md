# PC-Agent: ownership and extension points

Checked against `pc-agent/src/main/java` on 2026-10-02. This describes source structure, not hardware or pool certification. Read [the repository wiki](README.md), [standalone instructions](../../standalone/README.md), and the [PV-power design](../../../Solar-Miner-Node/PC-AGENT-PV-POWER-CONTROL.md) for the task at hand.

| Concern | Current owner | Extension rule |
| --- | --- | --- |
| HTTP boundary | `controller/` including `MiningController`, `AgentPowerController`, `TelemetryController` | Validate requests and delegate; no driver or pool business logic here. |
| CPU mining | `xmr/XmrMinerService`, `XmrConfigService`, `xmr/download/` | Keep XMRig/RandomX details here. |
| GPU/Pearl mining | `pearl/PearlMinerService`, `SrbDownloadService` | Keep SRBMiner/Pearl process, install-manifest cleanup and protocol details here. Read the [Pearl record](../../../PEARL-INTEGRATION.md). |
| Local power allocation | `mining/MiningService` | Owns total target and CPU/GPU allocation. The Node should not duplicate this allocation. |
| GPU driver power | `pearl/LocalGpuPowerService` | Detect capabilities, apply user bounds, write and read back limits. Unsupported GPUs remain start/stop only. The `pearl` package name currently hides a reusable hardware concern; consider moving it when another GPU miner uses it. |
| Proxy and fee | `mining/Proxy*`, `ManagedProxyService`, `StandaloneFeeGuard`, `FeeTransparencyService` | Fee validity gates start; keep pool/fee routing outside miner process implementations where possible. |
| Hardware sensors | `lowlevel/sensor/` | Report source, units and availability; missing is not zero. |
| Local settings and assessment | `mining/AgentControlSettingsService`, `NodeAssessmentService` | Node provides its economic/PV decision; agent controls local mining. |
| Operator UI | `src/main/resources/static/` | Render service state; do not reimplement fee or power decisions in JavaScript. |

## Verified seams and gaps

- `EarningsForecastService` reads `https://currency.solarminer.app/api/v1/public/mining-networks` for gross XMR/PRL/RVN/ETC/DCR/QTC forecast inputs and `/coin-prices` independently for market quotes, including BTC. It has no direct explorer, Kraken, CoinGecko or pool-stats URL. The agent refreshes successful data every ten minutes, withholds quotes after two hours without a refresh, and marks its last network copy stale after a central failure; provider provenance and the central hostname remain visible in the forecast. A market quote never certifies an available mining forecast. The public producer, schema, units and rollout gate are recorded in [currency data](currency-data.md).
- Mining navigation uses `GET /api/agent/local/miner-catalog` for local CPU/SRBMiner file availability only. `agent.js` loads it independently of the local overview; installation data never enables start controls. The UI groups catalog entries by software ID (one SRBMiner package for its supported coins), supports selecting multiple missing packages and starts those independent downloads together. Full operational state replaces the initial catalog, and late catalog responses cannot overwrite a newer overview. Node assessment is optional, loaded after rendering the overview with a five-second timeout; its failure does not mark the local agent offline. Verified by `MiningControllerValidationTest.installationCatalogOnlyChecksLocalFilesAndReflectsRemoval`; the earlier delayed-response Chrome fixture predates the grouped catalog, and a current visual browser pass remains open.
- Local dashboard APIs live exclusively below `/api/agent/local/**`; the SolarMiner-Node contract lives exclusively below `/api/agent/external/**`. There are no legacy/shared control aliases. `ExternalAgentController` exposes the Node's discovery, status, telemetry, configuration, pause/resume and target operations; `AgentPowerController` retains local settings and device limits.
- `AgentWriteAccessFilter` requires a same-origin browser context for every local API request. `GET /api/agent/external/identity` is the sole external exception: it is read-only and remains available for Node network discovery even when the operator disables remote control. Every other external route still requires `externalControlEnabled=true`; per-worker permission and benchmark admission remain additional checks after the global gate.
- XMRig and SRBMiner worker status includes nullable `acceptedShares` and `rejectedShares`. `MinerShareTelemetry` normalizes XMRig good/total values and SRBMiner's direct or nested share objects; values are reset for each process session and hidden for stopped workers. The Core and Node miner-details contracts preserve these counters verbatim; missing counters mean the miner API does not report them, not zero accepted shares. External Node status remains limited to selected, coin-assigned workers while the global external-control gate is enabled. `MinerShareTelemetryTest` and `MinerAgentControllerConfigurationTest` cover parsing and transport, but live miner/pool comparison is still required. This is miner-native telemetry, not a pool-accounting source of truth.
- All power-control commands are serialized with benchmark admission through `BenchmarkSessionService`. While a benchmark is running, local `/target` and Node `/external/*` target/pause/resume requests return HTTP 409; serialization closes the race where a command passed an idle check just as a benchmark began.
- `MiningService.setTarget` allocates a total target through the `MinerFactory` adapters; it no longer depends on individual miner services (see [miner adapter architecture](#miner-adapter-architecture-2026-10-10)).
- `LocalGpuPowerService` controls NVIDIA caps through `nvidia-smi` UUIDs and AMD caps through AMD-SMI UUID/BDF identifiers. Linux AMD additionally supports the kernel `amdgpu` hwmon `power1_cap` interface keyed by PCI BDF, so ROCm is not mandatory. A card is advertised as dynamically controllable only after a same-value write and readback succeed; a code path existing is still not proof of verified hardware behavior.

### GPU power-target verification (2026-10-04)

- Windows host probe: `nvidia-smi --query-gpu=index,uuid,name,power.min_limit,power.max_limit,power.limit,power.draw --format=csv,noheader,nounits` returned a GeForce RTX 2080 Ti with UUID `GPU-a823577d-6deb-5fcf-1309-ab2902b5f1f4`, driver range 100–366 W and current limit 300 W. The running Agent's read-only `/api/agent/local/power-control` response reported `supportsDynamicPowerScaling=true` for that GPU. From the sandbox account, `nvidia-smi -i <UUID> -pl 300` failed with `Insufficient Permissions`; readback remained 300 W. The unchanged-value write tested permission without changing the host limit. This does not establish the Agent process's own Windows token, but demonstrates that readable limits and the reported capability do not guarantee a writable target. The standalone launcher starts Java without elevation.
- Linux NVIDIA uses the same `nvidia-smi` query, `-pl` write and readback. AMD first uses AMD-SMI (`list/static/metric/set`) and falls back to the kernel's `amdgpu` hwmon power-cap files. Both paths require write permission and verify the unchanged current limit before reporting support. The NVIDIA Docker overlay exposes GPUs with `compute,utility`; the runtime image does not set a non-root `USER`. No real Linux NVIDIA or AMD changed-limit hardware probe has been completed yet.
- On either OS, `LocalGpuPowerService.setTotalPowerTarget` returns false when write/readback fails, and `MiningService` stops GPU mining and attempts a CPU-only fallback for the global target. Discovery now probes actual permission with a same-value write, multi-GPU writes use the live pre-write snapshot for transactional rollback, and original limits are persisted to `gpu-power-recovery.json` before the first change. Hardware acceptance still needs a permitted Agent process, a changed-limit write, readback, process-kill recovery and restoration on every supported driver/OS family.
- The power-efficiency sweep groups cards only when vendor, model, coin, algorithm and driver/user power bounds match. One reference card measures the descending curve; sibling cards validate its best candidate concurrently and move upward by the configured step until each card proves stable. References for different coin/algorithm cohorts initially fill otherwise-waiting sibling GPUs. There is no batch barrier: completing a reference immediately unlocks its same-coin validations, which are preferred as their concrete devices become free; otherwise an idle device starts the next coin reference. Session-scoped fallback overrides prevent one concurrent worker from clearing another's route. Profiles remain keyed by physical device ID and algorithm, so a model-level result is never accepted without per-card temperature, hashrate, pool and rejected-share verification. The session API exposes the planned queue, live sample count, completed steps, reference start group and an approximate ETA; ordinary Pearl benchmark sampling already measures configured GPUs concurrently.
- A cancelled or failed efficiency session can be resumed while the Agent process remains alive. Resume reuses only `COMPLETE` runs whose device/coin/algorithm and reference-vs-validation role still match the freshly discovered plan; cancelled partial curves remain visible but rerun, and never overwrite an earlier fully validated stored profile. Explicit restart ignores the checkpoint and schedules every run again. The checkpoint is intentionally session-local rather than inferred from persisted profiles after an Agent restart.
- Completed and interrupted sweep profiles feed the existing standalone benchmark-sharing path. With explicit benchmark consent enabled, every measured watt point is uploaded to admin-portal's separate efficiency-curve table; disabled consent retains the batch for the existing one-time prompt. Device IDs use the same participant-scoped UUID pseudonym as ordinary benchmarks, large curves are chunked at 512 points, and a no-stable-result curve still contributes its instability measurements without becoming a local best profile.
- The global PV target is deliberately not persisted: a restarted agent begins with no target and never restarts mining from a stale Node request. `PowerBudgetPlanner` is the pure CPU/GPU allocator used by `MiningService`; `PowerApplicationState` records the last requested, planned and applied target plus a partial/failure reason. The power-control response retains its existing fields and adds this result information additively. Dynamic GPU limits and process starts still require host verification.
- The miner catalog exposes install/remove actions. Removal stops the selected miner, deletes its executable and tracked SRBMiner package files, and preserves pool/wallet configuration.
- The installed miner detail view also exposes removal. External resume/target operations report success only when each requested CPU/GPU worker starts; the Node records a miner state lock only after the controller action succeeds, so failed starts can be retried on a later scheduler tick.
- The shipped standalone instructions describe a local embedded proxy and explicit miner installation. Verify release assets and actual fee routes during rollout, especially for new coins.
- The standalone `/benchmarks.html` page supports live measurement and sequential runs of configured XMRig/SRBMiner paths. Each worker is sampled every two seconds until it has twelve valid positive-hashrate observations; a worker that stops after becoming active is reported as incomplete, and the session remains manually cancellable. A sequential run treats configured CPU/GPU workers as expected immediately after its start command and allows 95 seconds for the first active status, so SRBMiner's pool/API warm-up is not misclassified as a skipped worker. Sequential runs restore managed miners that were running before the run, based on their managed process rather than Pearl's pool-health-gated display status. Sessions summarize per-device median hashrate and available power, compare against the Admin public match API, and retain the independent default-off periodic benchmark-sharing choice. Shared payloads use a random participant identity and UUID-derived device pseudonyms; they do not include pool credentials or general sensor data.
- On Windows, XMRig and SRBMiner installers classify a Defender/PUA `FileSystemException` as `BLOCKED_BY_ANTIVIRUS` and show a Protection history guide in the Mining catalog. Retrying remains an explicit user action after reviewing the detection. SRBMiner is pinned to 3.7.3 on Windows and Linux: upstream makes its architecture-specific PearlHash kernels the default for NVIDIA SM86, SM89 and SM120 in that release, while SRBMiner retains its standard path for the other supported NVIDIA generations. The agent continues to select the exact device from `--list-devices` with `--gpu-id`; it does not pass the removed `--pearl-k1`/`--pearl-k2` switches. A version marker prevents an older or unversioned executable from being treated as installed, so upgrading remains an explicit, checksum-verified installation action. This is documentation/CLI evidence, not live certification of every GPU family, driver and algorithm.
- The Worker table opens the selected worker's persisted XMRig/SRBMiner console in a modal, polls its per-worker console endpoint incrementally, follows new output while the view stays at the bottom and offers the existing full-log download. Assignment remains on the explicit `Einrichten`/`Ändern` button. Unassigned workers explain why no console exists; external miner output intentionally remains verbatim while all surrounding UI text is in the closed German/English catalog.
- Windows LibreHardwareMonitor is opt-in: the Agent no longer starts it from the application-ready lifecycle. The local Telemetry UI's explicit start/restart flow is the only Agent path that asks for elevation. Before launch, the Agent writes `/storage/enabled=false` to the monitor config, disabling storage/SMART discovery at the source rather than merely omitting returned storage readings. This protects against repeated Windows storage-helper prompts observed on a fresh Windows 11 host while keeping CPU/GPU sensor telemetry available after consent.
- Linux RAPL discovery resolves only the selected `/sys/class/powercap/*rapl*` class entry and then performs a depth-bounded walk without following links below it. Following sysfs `device`, `subsystem` or `power` links can cycle back to an ancestor; the former recursive scan could spin forever while holding the sensor monitor, which then blocked telemetry, overview, worker and benchmark reads. `LinuxSensorReaderTest` reproduces those link cycles. Wallet and Worker initial loads additionally use the shared eight-second JSON timeout so a future producer failure is shown instead of leaving the configuration areas indefinitely blank.
- The overview provides `installDirectory` in Monero and Pearl readiness. After a Defender block, the loopback Mining UI offers a button to request a narrowly scoped exclusion; see the next bullet for elevation and verification behavior.
- After a Defender-blocked Windows install, the loopback UI can request an exclusion for only that coin's known install directory. `WindowsDefenderExclusionService` starts a PowerShell helper through `Start-Process -Verb RunAs`; the elevated helper adds the path with `Add-MpPreference` and confirms it through `Get-MpPreference`. The browser receives a success/error result after the UAC flow. The API requires a loopback peer, loopback Host/Origin on the same port, and `BLOCKED_BY_ANTIVIRUS`. This requires the PC-Agent JVM to run natively on Windows; a Linux/Docker agent cannot administer the Windows host. Defender policies can still reject the change. Runtime/UAC behavior has not been verified on a Windows host.
- `MinerProcessRegistry` checks OS process command names for XMRig and SRBMiner-MULTI, so the overview recognizes instances started outside the current Java process and duplicate starts are refused. Coin stop and Spring shutdown terminate matching miner processes and descendants on Windows and Linux. An external process is shown as running, but its pool health, GPU attribution and hashrate remain unknown because its local API/session is not adopted.
- Successful Node-originated `/api/agent/external/*` commands append a timestamped English `[Remote Control]` entry to the XMRig log and to aggregate plus per-GPU Pearl logs for externally enabled workers. Changes to per-worker external-control permission are logged to that worker's miner console as well. These entries use the same persisted console files and polling/download API as miner output; rejected/failed actions are not recorded as successful changes.

## Miner adapter architecture (2026-10-10)

The clean-code refactoring (see the 2026-10-10 work-log entry and `../../REFACTORING-HANDOVER.md`) established two closed seams that every future coin/miner work must respect.

**Closed coin and state enums (`coin/`).** `Coin` is the single coin identity (id, ticker, algorithm plus aliases, device kind, experimental flag) with the selection helpers `miningCoins()`, `gpuCoins()`, `sharedSrbCoins()`, `assignableTo(cpuWorker)`, `byAlgorithm()` and `byIdOrNull()`. A new coin is one enum entry plus an adapter; coin literals in controllers/services are a defect. State enums `DownloadState`, `SweepRunState`, `SweepMode`, `ProxyMode`, `FeeRollMode`, `BenchmarkMode`, `WorkerCoinPolicy`, `WorkerIds` and `mining/ProxyLifecycle` replace status/mode magic strings. Iron rule: every enum wire name is a REST contract — the UI and Node read `QUEUED/RUNNING/COMPLETE`, `READY/DOWNLOADING`, `running/starting` etc. — so enums stay internal and getters return `.wireName()`. Never rename a wire name without a compatibility proof; `ProxyOverviewWireFormatTest` is the model for pinning a wire format.

**Adapter seam (`miner/`).** `CoinMiner` (lifecycle, `setPowerCap`, `updateProxyRoute`, `setupComplete()`, `appendBenchmarkEvent`), `CpuMiner` (+`readyForStart`, `savedRoute()`) and `GpuCoinMiner` (per-GPU control, `configuration/applyConfig/validateConfig`, `reportedAlgorithm`) define the shared semantics; coin-specific process, config-file and protocol knowledge lives only in the adapters: `xmr/XmrMinerService implements CpuMiner` (XMRig login parsing stays there), `pearl/PearlMinerService implements GpuCoinMiner` and `miner/SrbGpuCoinView` (per-coin delegate onto `pearl/GpuCoinMinerService`, which keeps its package deliberately). `MinerFactory` (`miner`, `cpuMiner`, `gpuMiner`, `srbGpuMiner`, `gpuMiners`, `supports`) is the only lookup for orchestration (`MiningService`, `EconomicPlanningService`, benchmark/sweep services, `WorkerAssignmentService`, `MiningController`, `AgentPowerController`). Orchestration branching on a coin id is a defect; add or extend an adapter instead.

**Local REST shape.** `/{coin}/download`, `/{coin}/remove` and `/{coin}/configuration` are the generic local routes (GPU removal stops all GPU runs because SRBMiner is one shared installation). `ProxyOverview` is coin-agnostic: `coinRoutes[]` plus a `@JsonAnyGetter` that re-emits the legacy flat `<coinId>Url`/`<coinId>FeeReady` fields Solar-Miner-Node still reads. External Node routes (`/api/agent/external/monero|pearl/configuration`) remain coin-named by design; migrating Node to generic routes is a separate cross-repository task (change Node first, then delete agent routes).

## Adding a miner

Document algorithm, device capability, installer provenance, process lifecycle, status units, power-control semantics, fee route and failure behavior. Keep the new miner's executable/API adapter in its own package. Add a shared interface only where two or more implementations have the same semantics; avoid a generic interface that hides unsupported operations. Follow the [coin integration guide](../../../NEW-MINING-COIN-GUIDE.md) and record real pool/fee accounting evidence before marking support complete.

The local `MinerCatalogService` is the selection seam: it owns per-coin selected miner IDs and presentation metadata, while existing lifecycle services remain the authority for whether that choice can safely start. Its API is additive (`GET /api/agent/local/miner-options`, overview `selectedMiner`/`miners`, and `POST /api/agent/local/{coin}/miner`). A catalog registration alone is never an implementation: wire a new miner to the process, console, stats, power, proxy/fee and installer integrity seams first. See [miner candidates](pc-agent-miner-candidates.md).

## Local live-state delivery (2026-10-05)

The managed proxy startup gate checks `GET http://127.0.0.1:<proxy-api-port>/api/health` after launching its child. Each launch passes a fresh `proxy.health-instance-id`; the returned `service` and `instanceId` must both match before the gate opens. A live PID or a reachable API port alone is insufficient. Published older proxy releases without `/api/health` use `/api/network/ip` as a compatibility fallback until an updated proxy release is available. The blocking browser gate also reads the Agent's `/api/agent/local/proxy-gate` every two seconds while visible, so a missed SSE update cannot strand the popup. This checks process/API identity, not coin listeners or fee readiness; miner starts retain their separate readiness gates.

`AgentEventController` serves the local `GET /api/agent/local/events` Server-Sent Events stream. It sends an initial `overview` event to every subscriber and subsequently emits a new serialized `MiningController.overview()` only when its one-second state observation changes. This covers asynchronous SRBMiner process monitors, driver readings and installer progress; the mining page refreshes its overview and incremental console only in response to that event (plus initial/manual refresh and reconnect), rather than polling continuously in the browser. The stream is local-agent UI state only; it introduces no Node, pool, fee or cross-repository wire contract.

The sibling proxy consumes the PC-Agent GPU relay's `solarminer.route` preamble before SRBMiner sends its first frame. A route-only relay connection is not a visible miner session in the proxy dashboard; `Miner connected` begins with actual miner traffic. The updated proxy must be included in the standalone Agent build or deployed alongside an external Agent.

For managed GPU miners, `MINING` denotes an active miner process even while pool/API health is still being checked. The separate `poolHealthy` and connection-detail fields describe pool readiness; a stopped process or explicit pause is not inferred from a temporary missing hash rate. `WorkerAssignmentService` matches the miner's technical algorithm identifiers (`kawpow`, `etchash`, `blake3_decred`, `quantus`) when resolving assigned GPU workers. The shared browser row mapper uses those same identifiers to associate telemetry and pool rows with the display coin.

The managed RVN/ETC/DCR/QTC GPU monitor reads SRBMiner's positive `hashrate.gpu.total`, then `hashrate.1m`, then legacy `hashrate.1min`. A zero/missing API sample or brief API failure retains the last positive display rate for at most 20 seconds in the same running process. Pool/worker health checks still use the raw sample. A stopped, failed or restarted process does not retain the old rate; after the grace period a real loss becomes zero. The intermittent Quantus API sample shape still needs a live capture on the operator's machine.

# RVN / ETC GPU path (prepared 2026-10-03)

`pearl/GpuCoinMinerService` adds separate RVN/KAWPOW and ETC/ETCHash SRBMiner configurations and per-GPU processes. It reuses Pearl's SRBMiner installer and physical GPU mapping, while `MinerProcessRegistry` marks new-coin PIDs so Pearl's external-process detection and stop path cannot claim them. `MiningService` dispatches the selected GPU coin for power targets and remote control. `ProxyConfigurationService` reserves 3336/3337, checks a live Stratum listener and a loaded house fee target before either new coin starts; `StandaloneFeeGuard` and the process monitor stop it if that route disappears. The local Mining UI exposes both coins and their own pool, wallet, worker and GPU selections.

The associated [integration record](rvn-etc-integration.md) contains the observed wire contract, test evidence and remaining fee/proxy/accounting gates. Both local forms now offer Kryptex regions, a custom pool and an explicitly confirmed SolarMiner house payout resolved from the fee backend. Neither coin is released for mining yet.

## Persistent Node profile and Mining UX (2026-10-03)

See [the verified UX/profile record](pc-agent-ux-profile.md). External dispatch now uses persisted per-device workerCoins instead of the viewed/preferred activeCoin; none excludes a worker from Node starts, stats and capacity. Local benchmarks remain independent. New installations require explicit device assignment.

## Gesamtgestaltung (2026-10-03)

Alle sechs UI-Seiten verwenden workspace.js/workspace.css für gruppierte Navigation, mobile Bedienung und gemeinsame Zustände. Aufgaben, Designentscheidungen und Browser-Evidenz stehen im [Gesamtkonzept](pc-agent-design-concept.md). Hardware-Grenzen werden explizit angewendet, Proxy-Suche ist von Auswahl/Aktivierung getrennt, und die Übersicht addiert keine Hashraten verschiedener Algorithmen. Lokale API-Verträge und Hardware-Freigaben bleiben unverändert.
